## ПРОБЛЕМА

Классический фаззинг (Echidna, Foundry Forge) генерирует случайные мутации байт-кода или аргументов. Это хорошо находит простые переполнения, но **бессильно против сложных нарушений бизнес-логики** в DeFi-мостах L1-L2 или ZK-компонентах. Вероятность случайно угадать правильную последовательность из 10 транзакций для взлома стремится к нулю.

Суть научного исследования (R&D):
Разработка "направляемого ИИ" (AI-Guided) генератора транзакций. Вместо случайного перебора (Brute-force) используется языковая модель (LLM) или обучение с подкреплением (RL). Нейросеть выступает в роли "сетевого аналитика": она изучает исходный Solidity-код, строит граф зависимостей функций, понимает экономический смысл контракта и целенаправленно генерирует сложные сценарии (цепочки JSON-RPC пакетов), пытаясь нарушить зафиксированные инварианты.

### ФАЗА 3 — Разработка парсера Solidity (Модуль 1)

**Цель:** научить систему читать и понимать смарт-контракт.

#### Архитектура модуля

```
.sol файл
    │
    ▼
Парсер (Python)
    │
    ├── извлекает функции и их сигнатуры
    ├── извлекает переменные состояния
    ├── извлекает события (Events)
    └── находит явные инварианты (require / assert)
    │
    ▼
Структурированный JSON
    │
    ▼
Системный промпт для LLM
```

#### Пример выходного JSON парсера

```json
{
  "contract_name": "LendingPool",
  "state_variables": ["totalDeposits", "userBalances", "borrowedAmount"],
  "functions": [
    {"name": "deposit",  "inputs": ["uint256 amount"], "modifiers": ["nonReentrant"]},
    {"name": "borrow",   "inputs": ["uint256 amount"], "modifiers": ["nonReentrant"]},
    {"name": "withdraw", "inputs": ["uint256 amount"], "modifiers": ["nonReentrant"]}
  ],
  "invariants": [
    "totalDeposits >= borrowedAmount",
    "userBalances[msg.sender] >= 0"
  ]
}
```

**Критерий завершения фазы:** на входе `.sol`-файл, на выходе промпт который корректно описывает контракт локальной LLM.

**Рекомендация агенту:** помоги студенту использовать библиотеку `slither` для парсинга AST Solidity вместо regex — это надёжнее.

### ФАЗА 4 — Интеграция с LLM (Модуль 2)

**Цель:** LLM генерирует структурированные сценарии атак.

#### 4.1 Структура системного промпта

```
РОЛЬ: ты эксперт по безопасности смарт-контрактов.
КОНТРАКТ: {описание из парсера}
ИНВАРИАНТЫ: {список инвариантов}
ЗАДАЧА: сгенерируй цепочку транзакций которая нарушит один из инвариантов.
ФОРМАТ ОТВЕТА: строго JSON, без пояснений.
```

#### 4.2 Структура выходных данных LLM

```json
{
  "scenario_name": "Reentrancy via borrow-withdraw",
  "target_invariant": "totalDeposits >= borrowedAmount",
  "transactions": [
    {"function": "deposit",  "args": [1000], "sender": "attacker"},
    {"function": "borrow",   "args": [900],  "sender": "attacker"},
    {"function": "withdraw", "args": [1000], "sender": "attacker"}
  ],
  "expected_violation": "баланс уходит в минус после withdraw"
}
```

**Критерий завершения фазы:** LLM стабильно возвращает валидный JSON с цепочками транзакций при разных входных контрактах.

### ФАЗА 5 — Интеграция с Anvil и цикл обратной связи (Модуль 3)

**Цель:** исполнить сценарий и вернуть результат в ИИ для следующей итерации.

#### Архитектура цикла

```
JSON-сценарий от LLM
        │
        ▼
   Anvil (форк сети)
        │
   исполняем транзакции последовательно
        │
        ├── читаем EVM Logs
        ├── проверяем инварианты
        └── фиксируем изменения состояния
        │
        ▼
  Результат: SUCCESS / FAIL + данные о состоянии
        │
        ▼
  Передаём обратно в LLM:
  "атака не сработала, инвариант устоял.
   Состояние после: {...}. Попробуй другой порядок."
        │
        ▼
  Новый сценарий → следующая итерация
```

#### Формат обратной связи в LLM

```json
{
  "iteration": 3,
  "result": "FAIL",
  "reason": "withdraw reverted: insufficient balance",
  "state_after": {
    "totalDeposits": 1000,
    "borrowedAmount": 900,
    "attacker_balance": 0
  },
  "next_action": "измени порядок — попробуй withdraw перед полным погашением borrow"
}
```

**Критерий завершения фазы:** система автоматически выполняет минимум 5 итераций без ручного вмешательства, логируя каждую попытку.

### ФАЗА 6 — Фаззинг ZK-инфраструктуры и мостов (Модуль 4)

**Цель:** применить систему к реальной сложной цели.

#### 6.1 Выбор цели
- Упрощённый контракт моста Optimism или Arbitrum (публичные репозитории)
- Контракты с уже известными историческими уязвимостями — для верификации что система их воспроизводит

#### 6.2 Ключевые инварианты моста для проверки

```
INV-1: баланс токенов на L1 >= сумма выпущенных токенов на L2
INV-2: одно сообщение не может быть исполнено дважды (replay attack)
INV-3: только валидный proof разблокирует средства на L1
INV-4: операция withdraw требует предварительного deposit той же суммы
```

#### 6.3 Метрики прогона
- Количество итераций до нахождения нарушения инварианта
- Сравнение с классическим Echidna на той же цели
- Время выполнения на идентичных сценариях

**Факт (Фаза 6.5, часть 1, завершено):** реализована каскадная схема — сначала LLM ищет уязвимость самостоятельно (контекст собран автоматически через Slither, без подсказки порядка действий), и только при неудаче за 8 итераций — получает описание с рекомендованным порядком, начиная с чистой истории попыток. Серия N=30 прогонов на `SimpleBridge.sol`:

| Показатель | Значение |
|---|---|
| Найдено без подсказки | 20/30 (66.7%), 95% ДИ [48.8%, 80.8%] |
| Найдено только с подсказкой | 7/30 (23.3%) |
| Не найдено даже с подсказкой | 1/30 (3.3%) |
| Найдено всего | 27/30 (90.0%), 95% ДИ [74.4%, 96.5%] |
| Медиана итераций до находки | 2.5 (без подсказки), 1 (с подсказкой) |

N=30 обосновано формулой доверительного интервала Уилсона (p≈0.5 → точность ±18 п.п.). Сравнение с Echidna — часть 2, ещё предстоит: нужны `echidna_*()` property-функции в контракте (сейчас их нет) и общая единица бюджета сравнения (Echidna считает `testLimit` в транзакциях, LLM-фаззер — `MAX_ITERATIONS` в целых сценариях).

**Факт (дополнение, N=40 объединено):** повторная серия N=10 дала другой % без подсказки (40.0% против 66.7%), но доверительные интервалы двух серий широко перекрываются — статистически не значимая разница, ожидаемый разброс на малых выборках. Объединили в N=40: **60.0% без подсказки [44.6%, 73.7%], 92.5% всего [80.1%, 97.4%]** — точнее любой из двух серий по отдельности, это финальная цифра для Фазы 7.

**Факт (Фаза 6.5, часть 2, завершено):** Echidna установлена, написан harness `SimpleBridgeEchidnaTest.sol` с тремя `echidna_*()`-свойствами (аналоги INV-1/2/3). Единица сравнения — время до первой находки (не `testLimit`/`MAX_ITERATIONS`, они не сопоставимы напрямую). Серия N=10 независимых прогонов (`testLimit: 50000`, отдельный seed каждый): **10/10 (100%) нашли INV-3, среднее время до находки ~1.18 сек**.

Важная методологическая деталь: чтобы сравнение было честным, первая версия harness'а была переписана — реентранси сделана opt-in (`armReentry()`, аналог `setAttackParams()` у LLM), иначе Echidna получала бы атаку "бесплатно", уже встроенной в контракт, и решала бы принципиально более простую задачу, чем LLM.

### ФАЗА 7 — Анализ результатов и оформление

**Цель:** получить измеримый результат и оформить исследование.

#### 7.1 Сравнительная таблица (заполняется по итогам)

| Метрика | Echidna (классика) | ИИ-фаззер (результат работы) |
|---|---|---|

| Нашёл нарушение логики моста | ❌ | ? |
| Количество итераций до находки | 100 000+ | ? |
| Требует понимания кода | ❌ | ✅ |
| Генерирует объяснение атаки | ❌ | ✅ |

**Факт (Фаза 6.5, части 1+2, обе завершены):**

| Метрика | Echidna (harness, N=10) | LLM-фаззер (N=40) |
|---|---|---|
| Нашёл INV-3 | 10/10 (100%) | 37/40 (92.5%), ДИ [80.1%, 97.4%] |
| Без ручной подготовки под контракт | Нет — harness писал человек | 24/40 (60.0%), ДИ [44.6%, 73.7%] — контекст автоматический |
| Среднее время до находки | ~1.18 сек | медиана 258 сек/прогон |
| Объясняет находку текстом | Нет | Да, но это не доказательство более глубокого понимания — побочный текстовый продукт того же вызова |

**Честная интерпретация (обязательно для отчёта, не только цифры):** Echidna быстрее на этом конкретном примере не потому что случайный перебор эффективнее направленного поиска, а потому что harness (написанный человеком вручную, несколько итераций правок) свёл пространство поиска до 3-4 действий. Настоящая разница между подходами — не в скорости перебора, а в том, что подготовку эквивалентного по чистоте пространства поиска LLM делает автоматически (через Slither), а Echidna требует этого от человека на каждый новый контракт. Кроме того, исходный тезис работы — про цепочки из 10 транзакций на реальных мостах, где комбинаторика делает brute-force безнадёжным; `SimpleBridge.sol` — намеренно неглубокий учебный пример (3 шага), и на такой глубине методы неразличимы. Это ограничение демонстрационного контракта, а не опровержение общего тезиса.

## РЕКОМЕНДАЦИИ ДЛЯ ИИ-АГЕНТА

1. **Контекст студента:** уровень — начинающий в Web3, есть базовые знания Python и ИБ. Не предполагай глубокого знания Solidity или EVM.

2. **Приоритет движения:** лучше завершить одну фазу полностью, чем начинать несколько. Каждая фаза имеет чёткий критерий завершения.

3. **Помощь с кодом:** когда студент просит помочь написать код — всегда добавляй комментарии объясняющие что делает каждый блок. Код должен быть читаемым, не оптимальным.

4. **Если студент застрял:** сначала объясни концепцию простыми словами, потом предложи минимальный рабочий пример, потом масштабируй.

5. **Финальная цель всегда в фокусе:** всё что делается — должно приближать к рабочему прототипу ИИ-фаззера и финальному bug bounty отчёту.

6. **Язык объяснений:** русский. Технические термины оставлять на английском (fuzzing, invariant, EVM, LLM).
