## ВАЖНОЕ АРХИТЕКТУРНОЕ НАБЛЮДЕНИЕ

`parser.py`, `llm_client.py`, `executor.py` — это НЕ библиотеки, которые импортирует `fuzzer.py`/`fuzzer_bridge.py`. Это отдельная, самостоятельная цепочка из трёх скриптов, работающая через промежуточные файлы в `build/`:

```
python parser.py contracts/X.sol       → build/contract_parsed.json, build/llm_prompt.txt
python llm_client.py                   → читает llm_prompt.txt → build/attack_scenario.json
python executor.py contracts/X.sol X   → читает attack_scenario.json → исполняет на Anvil
```

А `fuzzer.py` (Фаза 5) и `fuzzer_bridge.py` (Фаза 6) содержат **свои собственные копии** той же логики внутри себя (например, у `fuzzer.py` своя версия `parse_contract` с ДВУМЯ аргументами, а не с одним, как в `parser.py`). Работают оба варианта, но это два параллельных куска кода — при изменении логики парсинга/промптов нужно помнить, что править может понадобиться в двух местах.

| `TransactionNotFound` при деплое (в `executor.py`) | заменить `get_transaction_receipt(tx)` на `wait_for_transaction_receipt(tx)` — первая не ждёт майнинга |

| Общий баланс/учёт (`totalLocked` vs ETH) не ловит double-spend через reentrancy | при вложенных вызовах каждый уровень корректно уменьшает `totalLocked` на свою сумму — бухгалтерия "сходится" даже при двойном выводе одного `messageId`. Нужен отдельный инвариант на уровне событий (INV-3: подсчёт `Withdrawn`-событий по `messageId`) |
| LLM оборачивает JSON в пояснительный текст ("Here is the generated scenario...") | вырезать JSON по первой `{` и последней `}` в ответе вместо предположения что ответ начинается ровно с `{` |
| LLM путает порядок числовых/строковых аргументов (`amount`/`message_alias`) | парсить аргументы по типу значения (число → amount, иначе → alias), а не по фиксированной позиции |
| Одно и то же нарушение дублируется в отчёте на каждом шаге | `check_invariants()` пересканирует всю историю с начала на каждом шаге — дедуплицировать финальный список `violations` через `dict.fromkeys()` |

| LLM присылает список транзакций без внешней обёртки `{...}` | вторая стратегия разбора — оборачивает в `[...]`, восстанавливает структуру, если все элементы содержат `"function"` |

| `deposit` с пустым/нечисловым первым аргументом падал сырым Python-исключением | как и для `withdraw`, ищем первое численно-парсящееся значение среди `args` |

| **Главное архитектурное решение фазы:** регекс-починки JSON ненадёжны на 100%, LLM стохастична и постоянно находит новые способы сломать синтаксис | добавлен `"format": "json"` в запрос к Ollama API — режим constrained decoding, модель физически не может выдать невалидный JSON. ## КОД — contracts/SimpleBridge.sol (Фаза 6, ключевой контракт)

```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.0;

contract SimpleBridge {
    address public owner;
    uint256 public totalLocked;
    uint256 public totalMinted;

    mapping(address => uint256) public locked;
    mapping(address => bool) public validators;
    mapping(bytes32 => bool) public processedMessages;

    event Deposited(address indexed user, uint256 amount);
    event Withdrawn(address indexed to, uint256 amount, bytes32 messageId);

    modifier onlyOwner() {
        require(msg.sender == owner, "not owner");
        _;
    }

    constructor(address[] memory initialValidators) {
        owner = msg.sender;
        for (uint256 i = 0; i < initialValidators.length; i++) {
            validators[initialValidators[i]] = true;
        }
    }

    function deposit() external payable {
        require(msg.value > 0, "zero deposit");
        locked[msg.sender] += msg.value;
        totalLocked += msg.value;
        totalMinted += msg.value;
        emit Deposited(msg.sender, msg.value);
    }

    // ⚠️ БАГ: processedMessages[messageId] выставляется ПОСЛЕ внешнего
    // вызова — при реентрантном повторном вызове withdraw() с тем же
    // messageId защита от replay ещё не сработала.
    function withdraw(address payable to, uint256 amount, bytes32 messageId) external {
        require(validators[msg.sender], "not a validator");
        require(!processedMessages[messageId], "already processed");
        require(amount <= totalLocked, "insufficient bridge liquidity");

        (bool sent, ) = to.call{value: amount}("");
        require(sent, "transfer failed");

        totalLocked -= amount;
        totalMinted -= amount;
        processedMessages[messageId] = true; // слишком поздно

        emit Withdrawn(to, amount, messageId);
    }

    function addValidator(address v) external onlyOwner {
        validators[v] = true;
    }
}

// Контракт-атакующий: без него reentrancy физически невозможна
// (EOA не имеет receive()/fallback()).
contract MaliciousReceiver {
    SimpleBridge public bridge;
    bytes32 public messageId;
    uint256 public amount;
    uint8 public reentryCount;
    uint8 public maxReentries;

    constructor(address bridgeAddress) {
        bridge = SimpleBridge(bridgeAddress);
    }

    function setAttackParams(bytes32 _messageId, uint256 _amount, uint8 _maxReentries) external {
        messageId = _messageId;
        amount = _amount;
        maxReentries = _maxReentries;
        reentryCount = 0;
    }

    receive() external payable {
        if (reentryCount < maxReentries) {
            reentryCount += 1;
            try bridge.withdraw(payable(address(this)), amount, messageId) {} catch {}
        }
    }
}
```

**Три инварианта, которые проверяет `fuzzer_bridge.py`:**
- **INV-1:** `totalLocked` не может превышать реальный ETH-баланс контракта
- **INV-2:** `totalLocked` должен быть равен `totalMinted`
- **INV-3** (главный, добавлен уже в процессе отладки): ни один `messageId` не должен быть успешно выведен (`withdraw`) больше одного раза — проверяется через подсчёт событий `Withdrawn` по `messageId`. **Именно этот инвариант ловит реальный баг** — INV-1/INV-2 его пропускают, потому что при вложенных reentrancy-вызовах бухгалтерия (`totalLocked -= amount` на каждом уровне) остаётся математически согласованной с реальным балансом даже при двойном выводе.

**Ключевая деталь реализации `fuzzer_bridge.py`:** и `ATTACKER` (EOA), и `attacker_contract` (`MaliciousReceiver`) регистрируются как валидаторы сразу при деплое. Без этого реентрантный вызов `withdraw()` изнутри `receive()` падает на первом же `require(validators[msg.sender])`, потому что при межконтрактном вызове `msg.sender` — это адрес вызывающего контракта, а не исходный EOA.

## РЕЗУЛЬТАТ — успешный прогон fuzzer_bridge.py

```
Цель: INV-1

✅ Отчёт сохранён: build/fuzzer_bridge_report.json
```

LLM самостоятельно построила связку `deposit → setAttackParams → withdraw` (двухшаговая настройка атаки перед её запуском), без прямой подсказки готового решения — только по описанию функций и инвариантов в промпте.

**Важно (для честности будущего отчёта в Фазе 7):** результат нестабилен между прогонами. В одном из тестовых запусков баг был найден на итерации 1, в другом — не найден ни разу за 8 итераций. Это ожидаемо для локальной 7B-модели без файнтюна. Для Фазы 7 нужна количественная метрика (например 10 прогонов подряд, % успешных попыток, среднее число итераций до находки), а не единичный результат.

## РЕЗУЛЬТАТ — ФАЗА 6.5 (часть 1), СЕРИЯ ИЗ 30 ПРОГОНОВ (`run_bridge_stats.py 30`)

Ровно та количественная метрика, которой не хватало по итогам Фазы 6 (см. абзац выше). Прогнана каскадная схема (сначала blind, при неудаче — guided с чистой историей) на исправленной, инфраструктурно стабильной версии `fuzzer_bridge.py`:

| Показатель | Значение |
|---|---|
| Найдено **без подсказки** (stage=blind) | 20/30 (66.7%), 95% ДИ [48.8%, 80.8%] |
| Найдено **только с подсказкой** (stage=guided) | 7/30 (23.3%) |
| Не найдено даже с подсказкой | 1/30 (3.3%) |
| Инфраструктурные ошибки | 2/30 (6.7%) |
| Найдено ВСЕГО (blind+guided) | 27/30 (90.0%), 95% ДИ [74.4%, 96.5%] |
| Медиана итераций до находки | 2.5 (blind), 1 (guided) |

Доверительный интервал — Уилсона (не нормальная аппроксимация, та ненадёжна на малых N). N=30 выбрано по формуле `n ≈ z²·p(1-p)/h²`: при p≈0.5 (худший случай) даёт точность ±18 п.п. — компромисс между точностью и временем (полная серия — 134 минуты).

**Единственный полный провал (прогон 18):** не системная проблема — модель на всех 16 попытках (8 blind + 8 guided) стабильно указывала сумму `withdraw`, превышающую внесённый `deposit`. Конкретная, идентифицируемая причина, не архитектурная слабость подхода — стоит отметить в отчёте именно так, а не как "необъяснимую неудачу".

Полный размеченный итог с оговорками для раздела "Ограничения" — в отдельном файле `phase_6_5_summary.md`.

## РЕЗУЛЬТАТ — ФАЗА 6.5 (часть 2), СРАВНЕНИЕ С ECHIDNA (ФИНАЛ, N=40 с обеих сторон)

**Дозапустили Echidna ещё на 30 прогонов (seed 11-40) поверх первых 10 (seed 1-10) — специально ради равного N с LLM-фаззером, для честности сравнения.**

**Итог серии Echidna (N=40 независимых прогонов, `testLimit: 50000` каждый, честный opt-in harness):**

| Показатель | Значение |
|---|---|
| Найдено INV-3 | **40/40 (100.0%)**, 95% ДИ [91.2%, 100.0%] |
| Среднее время до первой находки | **1.20 сек** (медиана 1.15 сек, диапазон 1.10–2.15 сек) |
| Суммарное время серии | ~48 сек |

**Финальная сравнительная таблица (N=40 с обеих сторон):**

| Метрика | Echidna (harness, N=40) | LLM-фаззер (N=40) |
|---|---|---|
| Нашёл INV-3 | **40/40 (100.0%)**, ДИ [91.2%, 100.0%] | **37/40 (92.5%)**, ДИ [80.1%, 97.4%] |
| Без ручной подготовки под конкретный контракт | Нет — harness с `echidna_*()` писал человек | **24/40 (60.0%)**, ДИ [44.6%, 73.7%] — контекст автоматический (Slither) |
| Среднее время до находки | 1.20 сек | 256.3 сек (медиана 250.3 сек) |
| Разброс времени (мин–макс) | 1.10–2.15 сек | 29.0–1351.7 сек |
| Суммарное время серии | ~48 сек | 170.9 мин (2.8 часа) |
| Объясняет находку текстом | Нет | Да (`scenario_name`, `expected_violation`) — но это не доказательство более глубокого понимания, просто побочный текстовый продукт того же вызова |

**Честная интерпретация для отчёта (три отдельных, не сводимых друг к другу вывода):**
1. **По скорости на этом конкретном мелком примере** Echidna быстрее на четыре порядка (1.2 сек vs 256 сек) — но это заслуга маленького пространства поиска ПОСЛЕ ручной подготовки harness'а (4 функции, 3 логических шага), а не превосходство случайного перебора над направленным поиском как таковое. На таком узком пространстве оба метода неотличимы по содержательной эффективности.
2. **По инженерным затратам на подготовку** — разница настоящая: harness под Echidna требует ручной работы человека на каждый новый контракт (несколько итераций правок на шагах 2-3). LLM получает эквивалентную подготовку автоматически через Slither, без участия человека — это единственное по-настоящему масштабируемое преимущество подхода.
3. **Исходный тезис проекта был про цепочки из 10 транзакций** (реальные DeFi-мосты) — на такой глубине комбинаторика делает brute-force безнадёжным. `SimpleBridge.sol` — учебный, намеренно неглубокий (3 шага) пример; на такой глубине Echidna и LLM неразличимы по эффективности. Это ограничение демонстрационного контракта, а не опровержение общего тезиса — но именно так нужно написать в отчёте, не замалчивая.
4. **Стабильность результата тоже показательна сама по себе:** у Echidna разброс времени почти нулевой (1.10–2.15 сек) — детерминированный перебор, у LLM разброс огромный (29 сек – 22.5 мин) — прямое следствие стохастичности генерации. Это тоже честный пункт сравнения "по принципу", не только по итоговому проценту успеха.
