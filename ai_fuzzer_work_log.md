## Фаза 1 + Фаза 2 — 03.07.2026

### Что было сделано

Стартовали с нуля — без какого-либо опыта в Web3 и смарт-контрактах. Первый день был полностью теоретическим, плюс полная установка окружения.

**Теория (Фаза 1)** — разобрали пять блоков:

- **EVM и Solidity:** как устроен виртуальный компьютер Ethereum, что такое нода, стек/память/storage, как Solidity компилируется в байткод, что такое ABI. Ключевое понимание: газ защищает сеть от бесконечных циклов, каждый opcode стоит денег.
- **L1/L2 и мосты:** зачем нужны L2 (дороговизна Ethereum — платит пользователь), как работает мост (блокировка на L1 → минтинг на L2), почему мосты взламывают чаще всего — они хранят миллиарды и логика синхронизации между двумя цепочками очень сложная (примеры: Ronin $625M, Wormhole $320M).
- **Инварианты:** утверждения которые всегда должны быть истинными. `totalLockedOnL1 >= totalMintedOnL2` — классический пример для моста.
- **Классический фаззинг:** Echidna и Foundry работают через случайный перебор. Ограничение — не могут найти уязвимости требующие конкретной осмысленной последовательности.
- **LLM-компонент:** вместо случайных мутаций — модель читает код и рассуждает. Граф зависимостей функций помогает понять какие функции связаны и в каком порядке их атаковать.

**Установка окружения (Фаза 2):**

1. Foundry через `curl -L https://foundry.paradigm.xyz | bash` + `foundryup`
2. Ollama + скачка модели llama3 (~4.7 GB)
3. Python venv + зависимости: `web3`, `requests`, `slither-analyzer`, `py-solc-x`
4. Запуск Anvil, деплой `SimpleVault.sol`, проверочный `test_deploy.py`

### Что усвоено

- Нода — это просто компьютер с копией блокчейна. Тысячи нод = децентрализация.
- Газ платит пользователь всегда, именно поэтому L2 решает реальную проблему.
- Фаззер — это не генератор новых контрактов, а инструмент атаки существующего.
- В нашей архитектуре LLM — это и есть умный фаззер, заменяющий случайный компонент.

### Трудности

- **Пробел в пути к папке проекта** (`обучение /web`) ломал команды терминала. Решение: всегда брать путь в кавычки или экранировать `\ `.
- **venv указывал на системный Python** — pip устанавливал библиотеки в `/Library/Frameworks/...` вместо проекта. Первый venv пришлось пересоздать.
- **`py-solc-x` не был установлен** изначально — обнаружилось только при первом запуске скрипта.

### Идеи по улучшению

- Можно автоматизировать проверку окружения при старте: скрипт `setup_check.py` который за 10 секунд проверяет что Anvil запущен, Ollama отвечает, все модули импортируются.
- Вместо llama3 можно попробовать более мощную модель (например через API: GPT-4o, Claude) — качество генерируемых сценариев было бы значительно лучше уже на Фазе 5.

## Фаза 3 — 04.07.2026

### Что было сделано

Написали два модуля: `parser.py` и `llm_client.py`. Это первый день когда система начала реально "думать".

**parser.py** — использует Slither для анализа AST Solidity-файла. Извлекает:
- имя контракта
- переменные состояния
- функции с параметрами и видимостью
- инварианты через поиск `require`/`assert` по узлам AST

Из JSON строит структурированный промпт для LLM — не сырой код, а человекочитаемое описание контракта.

**llm_client.py** — HTTP-клиент к Ollama API. Отправляет промпт, получает JSON со сценарием атаки. На первом запуске LLM придумала Reentrancy Attack, на втором — replay attack.

### Что усвоено

- Slither работает с AST (абстрактным синтаксическим деревом) — это надёжнее regex. Парсер через regex сломался бы на любом нестандартном форматировании.
- `deposit()` не имеет аргументов в ABI потому что принимает ETH через `msg.value` — это особенность Solidity, не баг парсера.
- LLM иногда возвращает незакрытый JSON — модель просто обрезается по длине ответа. Это нужно обрабатывать в коде.

### Трудности

- **`slither-analyzer` не установился с первого раза** — выяснилось только при запуске `parser.py`. Причина та же: pip шёл в системный Python до пересоздания venv.
- **Ollama таймаут 120 секунд** — llama3 на CPU думает дольше. Увеличили до 300 секунд.
- **Незакрытый JSON от LLM** — модель иногда обрезает ответ. Решение: считать количество `{` и `}`, добавлять недостающие закрывающие скобки перед `json.loads()`.
- **Промпт слишком большой** — при первой попытке Ollama просто не ответила за 120 секунд. Пришлось оптимизировать формулировки.

### Идеи по улучшению

- Парсер сейчас извлекает только явные `require`/`assert`. Более умная версия могла бы анализировать семантику переменных — например, если есть `totalDeposits` и `balances`, автоматически создавать инвариант `totalDeposits == sum(balances)`.
- Промпт можно улучшить: добавить примеры известных атак (reentrancy, integer overflow, access control) как few-shot примеры — это значительно повышает качество генерации.
- Стоит добавить валидацию JSON-ответа от LLM по JSON Schema — сейчас если модель вернула не тот формат, скрипт падает с невнятной ошибкой.

## Фаза 4 — 05.07.2026

### Что было сделано

Написали `executor.py` — исполнитель транзакций с детектором инвариантов. Это самый важный модуль с точки зрения безопасности: именно он решает "найден баг или нет".

Три инварианта которые проверяются после каждой транзакции:
1. `balances[account] >= 0` — баланс не может быть отрицательным
2. `totalDeposits <= ETH на контракте` — учётная запись не должна "придумывать" ETH
3. `balances[account] <= totalDeposits` — нельзя иметь больше чем задепозировали все вместе

Для проверки детектора создали два контракта с намеренными багами:
- `VulnerableVault.sol` — reentrancy (неправильный порядок: сначала transfer, потом обновление баланса)
- `BuggyVault.sol` — забытое обновление `totalDeposits` в `withdraw()`

**Важное открытие про reentrancy:** атака не сработала через обычный аккаунт (EOA). Настоящий reentrancy требует атакующий смарт-контракт с `fallback()`-функцией, которая повторно вызывает `withdraw()` во время исполнения первого вызова. Обычный Python-скрипт так не может — второй вызов идёт отдельной транзакцией, к тому времени баланс уже обновлён.

`BuggyVault` сработал сразу — `totalDeposits (1000 wei) > ETH на контракте (500 wei)` после `withdraw(500)`.

### Что усвоено

- Детектор инвариантов — это не просто `assert` в Python, это чтение реального состояния блокчейна через `web3` после каждой транзакции.
- Reentrancy — это атака на уровне исполнения EVM внутри одной транзакции, не между транзакциями. Это принципиально важно для понимания класса уязвимостей.
- `wait_for_transaction_receipt` критически важен — без него транзакция может быть ещё не включена в блок когда мы читаем receipt.

### Трудности

- **`TransactionNotFound`** — использовали `get_transaction_receipt` вместо `wait_for_transaction_receipt`. Anvil майнит блоки не мгновенно, нужно ждать подтверждения.
- **Reentrancy не сработал** — потратили время на выяснение почему. Зато получили важное понимание разницы между атаками внутри транзакции и между транзакциями.
- **executor.py принимал имя контракта хардкодом** — пришлось переписать чтобы принимать имя через аргумент командной строки для переиспользования на разных контрактах.

### Идеи по улучшению

- Реализовать атакующий смарт-контракт на Solidity (`AttackContract.sol`) с `fallback()` — это позволит тестировать настоящие reentrancy атаки. Деплоить его вместе с целевым контрактом в одной сессии.
- Детектор сейчас проверяет только три хардкодных инварианта. Лучше генерировать инварианты динамически из вывода парсера — это сделает систему применимой к любому контракту, а не только к vault-паттерну.
- Добавить снапшоты состояния Anvil через `anvil_snapshot` / `anvil_revert` — тогда не нужно деплоить новый контракт на каждую итерацию, можно откатываться к начальному состоянию. Это сильно ускорит фаззинг.

## Фаза 5 — 06.07.2026

### Что было сделано

Написали `fuzzer.py` — главный оркестратор, который объединяет все модули в автономную петлю с обратной связью.

**Цикл работает так:**
1. Парсим контракт → структура + инварианты
2. LLM генерирует сценарий атаки (начальный промпт)
3. Деплоим свежий контракт на Anvil
4. Исполняем сценарий, проверяем инварианты
5. Если баг найден → сохраняем отчёт, стоп
6. Если нет → формируем фидбек-промпт с историей всех попыток → возвращаемся к шагу 2
7. Максимум 5 итераций

**Ключевая новинка — фидбек-промпт:** LLM видит историю предыдущих попыток и их результат. Она знает что уже пробовала и почему не сработало — это и есть обратная связь.

**Результат на BuggyVault:** баг найден на итерации 1. LLM сразу придумала `deposit(1000) → withdraw(500)` и детектор поймал нарушение.

### Что усвоено

- Обратная связь работает — история попыток реально помогает LLM не повторяться.
- Для простых контрактов LLM находит баг с первой итерации. Фидбек-механизм пригодится на сложных контрактах мостов в Фазе 6.
- Каждая итерация деплоит свежий контракт — это гарантирует изоляцию состояния между попытками.

### Трудности

- **`get_transaction_receipt` снова** — ошибка вернулась в `fuzzer.py` потому что копировали код из старого `executor.py` который ещё не был исправлен. Исправлено через `sed` одной командой.
- **LLM иногда добавляет "100 ether" вместо числа в wei** — парсер аргументов ломается на строке `"100 ether"`. Нужна более надёжная нормализация аргументов.
- **Нет изоляции между итерациями через снапшоты** — каждый раз деплоим новый контракт, это медленно и расходует тестовые адреса. На больших итерациях (50+) это станет проблемой.

### Идеи по улучшению

- **Снапшоты Anvil** — `anvil_snapshot` перед первым деплоем, `anvil_revert` перед каждой итерацией вместо нового деплоя. Ускорение в 3-5 раз.
- **Нормализация аргументов LLM** — добавить конвертер который понимает `"1 ether"` → `10**18`, `"100 gwei"` → `10**11`. LLM мыслит в человекочитаемых единицах.
- **Параллельные итерации** — запускать несколько экземпляров фаззера одновременно с разными seed-промптами. Первый нашедший баг побеждает.
- **Расширить инварианты** — сейчас проверяем только финансовые инварианты vault-паттерна. Для мостов нужны: уникальность messageID, соответствие L1/L2 балансов, запрет двойного исполнения.
- **Логирование в файл** — сейчас всё идёт в stdout. Добавить `fuzzer.log` с таймстампами для анализа после долгих прогонов.
- **Сравнение с Echidna** — запустить Echidna на тех же контрактах с тем же временным лимитом и сравнить количество найденных багов. Это даст количественную оценку преимущества LLM-подхода для финального отчёта.

## Фаза 6 — 25.07.2026

### Что было сделано

Написали `SimpleBridge.sol` — упрощённый мост L1 с двумя намеренными багами (по мотивам реальных инцидентов Ronin/Wormhole): анти-replay флаг `processedMessages[messageId]` выставляется ПОСЛЕ внешнего вызова в `withdraw()`, и добавление валидатора не требует кворума. Плюс `MaliciousReceiver.sol` — контракт-атакующий с `receive()` для реентрантного вызова, без которого атаку в принципе не воспроизвести (см. вывод Фазы 4).

Написали `fuzzer_bridge.py` (по образцу `fuzzer.py`) и `test_bridge_manual.py` — ручной sanity-тест без LLM, чтобы сначала убедиться что баг физически воспроизводим, и только потом гонять автоматику.

Это была самая долгая по количеству итераций фаза — прежде чем всё заработало, пришлось найти и починить целую серию реальных багов, каждый из которых дал отдельное понимание:

**1. Обнаружили старый баг в `executor.py` (не новый, тянулся с Фазы 4, просто не был раньше проверен):** `get_transaction_receipt(tx)` не ждёт майнинга и падает `TransactionNotFound`. Исправлено на `wait_for_transaction_receipt(tx)`. Заодно перепроверили всю Фазу 4 заново (4.1/4.2/4.3) — все три случая подтвердились корректно после фикса.

**2. Реентрантный `withdraw()` падал на `require(validators[msg.sender])`.** Причина: при вызове контракт→контракт `msg.sender` внутри вызываемой функции — это адрес ВЫЗЫВАЮЩЕГО контракта, а не исходный EOA. `attacker_contract` не был валидатором → реентрантный вызов сразу отбивался. Исправлено: регистрировать `attacker_contract` как валидатора в `deploy_bridge_and_attacker()`.

**3. После фикса #2 — `TypeError: get_logs() got an unexpected keyword argument 'fromBlock'`.** Версия web3.py в проекте новее той, под которую был написан код, и использует snake_case (`from_block`), а не camelCase (`fromBlock`).

**4. Самое важное открытие:** после фикса #2 и #3 reentrancy физически заработала (`reentryCount=2`, `attacker_contract` получил 2000 wei вместо 1000), НО первоначальные инварианты (INV-1: `totalLocked` vs ETH-баланс, INV-2: `totalLocked` vs `totalMinted`) это не поймали. Причина: при вложенных reentrancy-вызовах КАЖДЫЙ уровень вложенности корректно уменьшает `totalLocked` на свою сумму — бухгалтерия "сходится" с реальным балансом даже при двойном выводе одного и того же `messageId`. Пришлось добавить отдельный **INV-3**: подсчёт событий `Withdrawn` по `messageId` через `bridge.events.Withdrawn.get_logs()` — если один `messageId` встречается больше одного раза, это и есть double-spend через reentrancy.

**5. Автоматический прогон с LLM:** первая попытка упала с `JSONDecodeError: Expecting value: line 1 column 1` — оказалось, `response` от Ollama пришёл вообще пустым. Добавили диагностику в `ask_llm()` (печать HTTP-статуса и полного JSON при пустом/невалидном ответе) — на следующем прогоне диагностика показала, что модель на этот раз обернула JSON в пояснительный текст ("Here is the generated scenario..."), хотя промпт явно просит отвечать строго JSON. Исправлено: вырезать содержимое между первой `{` и последней `}` в ответе, а не полагаться на то что ответ начинается ровно с `{`.

**6. Тот же прогон показал:** модель перепутала порядок аргументов в `withdraw` (`amount` и `message_alias` местами) — `int("m1")` уронил бы шаг в `ValueError`. Сделали парсинг аргументов устойчивым к порядку: определяем `amount`/`message_alias` по типу значения (число → amount, иначе → alias), а не по фиксированной позиции.

**После всех фиксов:** ручной sanity-тест (`test_bridge_manual.py`) стабильно ловит `INV-3` (double-spend, `messageId` выведен несколько раз). Автоматический `fuzzer_bridge.py` нашёл баг **на первой же итерации** — LLM сама построила связку `deposit → setAttackParams → withdraw`, не видя готового решения, только описание функций контракта и списка инвариантов в промпте.

**Повторный прогон для проверки стабильности** дал другой результат — 8 итераций без находки. Это подсветило важный факт для будущего отчёта: одна успешная попытка не доказывает стабильность системы, нужна метрика по серии прогонов.

Заодно почистили дублирование одинаковых нарушений в отчёте (`check_invariants()` пересканирует историю с начала на каждом шаге — одно и то же нарушение "всплывало" по несколько раз в списке `violations`) через `dict.fromkeys()`, и добавили сохранение полной истории всех попыток (даже неудачных) в `build/fuzzer_bridge_debug.json` для последующего анализа.

### Что усвоено

- Reentrancy — это не просто "вызвать функцию дважды". На каждом уровне вложенности `msg.sender` меняется на адрес непосредственного вызывающего — это ломает наивные проверки прав доступа (`require(validators[msg.sender])`), но одновременно это и есть механизм, который позволяет атаке "выглядеть легитимной" на каждом шаге.
- **Инварианты уровня "общая бухгалтерия" (totals) — это не то же самое, что инварианты уровня "конкретная операция".** Double-spend может быть невидим для totals-инвариантов, если атака внутренне себя "балансирует" на каждом шаге. Для протоколов, где важна одноразовость операции (антиреплей, nonce, messageId) — нужен отдельный инвариант именно про уникальность, а не только про суммы.
- Диагностика важнее заглушек: молчаливое "не удалось распарсить JSON, попробуем снова" маскирует РАЗНЫЕ проблемы (пустой ответ / текст вокруг JSON / реально сломанный JSON) под одну и ту же ошибку. Явный вывод сырого ответа при сбое сразу показал, что проблема — не в скобках, а в обёртке текстом.
- Одного успешного прогона недостаточно, чтобы заявлять "фаззер работает" — нужна серия прогонов и статистика.

### Трудности

Полный список — в таблице "ПРОБЛЕМЫ" в `ai_fuzzer_progress_summary.md`. Ключевое отличие от предыдущих фаз: почти все баги в этой фазе были не в бизнес-логике контракта, а в инфраструктурном коде вокруг него (парсинг ответов LLM, работа с web3.py API, права доступа при межконтрактных вызовах) — то есть по мере усложнения цели растёт не только сложность самого контракта, но и сложность обвязки вокруг него.

### Идеи по улучшению

- **Стабильность LLM-фаззера нужно измерять, а не декларировать.** Прогнать `fuzzer_bridge.py` 10+ раз подряд, зафиксировать % успешных находок и среднее число итераций — это прямой количественный аргумент для Фазы 7, и без него утверждение "AI-фаззер эффективен" остаётся анекдотическим.
- **Более надёжный парсинг ответа LLM** — сейчас это набор последовательных костылей (снять markdown, вырезать по скобкам, определить тип аргумента). Правильное решение — JSON Schema validation с явным сообщением об ошибке модели и повторным запросом ("твой прошлый ответ не прошёл валидацию, вот почему, попробуй снова"), а не молчаливые эвристики.
- **INV-3 сейчас завязан на полное сканирование истории событий с начала (`from_block=0`) на каждом шаге** — на длинных сценариях это будет линейно замедляться. Можно кэшировать уже просмотренные события между шагами одного сценария.
- Всё ещё актуально из Фазы 5: снапшоты Anvil вместо передеплоя контракта на каждой итерации значительно ускорили бы прогон, особенно для серии из 10+ прогонов на стабильность.

## Фаза 6.5 (часть 1) — метрика стабильности — 15.08.2026

### Что было сделано

Начали с ревизии кода перед тем как гонять серию прогонов на стабильность — и сразу нашли системную проблему: `fuzzer_bridge.py` вообще не использовал парсер (`parser.py`/Slither) для контракта моста. Промпт строился из вручную написанной строки `BRIDGE_CONTEXT`, в которой прямым текстом был прописан рекомендуемый порядок атаки. Это подрывало главный тезис работы — что LLM анализирует код сама, а не выполняет данный ей рецепт.

**Архитектурное решение:** переделали `fuzzer_bridge.py` на каскад:
1. Этап **"blind"** — контекст собирается автоматически через Slither (`parse_contract_by_name()`, `build_bridge_context_blind()`), без рецепта атаки, только сигнатуры функций + список инвариантов (список инвариантов — это законно, аналог `echidna_*()`-функций в классическом фаззинге, а не подсказка решения).
2. Если blind не находит баг за 8 итераций — этап **"guided"** с прежним `BRIDGE_CONTEXT`, но **с чистой историей попыток** (иначе сравнение blind vs guided было бы нечестным — guided-промпт "видел" бы неудачные blind-попытки).
3. Итоговый отчёт помечается `stage: "blind"/"guided"`, что дало возможность считать три категории результата вместо одной.

**Дальше — долгая цепочка инфраструктурных находок**, каждая обнаружена только благодаря тому, что стали гонять не единичные прогоны, а серии (сначала по 3, потом по 5). Единичные прогоны, которыми ограничивались раньше, не могли выявить эти проблемы — они проявлялись статистически, не на каждом прогоне:

1. **"Слепой" контекст (реальные типы Solidity из Slither: `address`, `bytes32`) заставил модель присылать нереалистично оформленные значения** — голые адреса и hex без кавычек (`[attacker_contract, 0x001]`), Solidity-нотацию единиц (`1 ether`). Оба ломали JSON. Добавили явный `ARGS_FORMAT_NOTE` в промпт (описание формата вывода — не подсказка решения) и `sanitize_llm_json()` — регекс-починка постфактум для случаев, когда модель промпт всё равно не соблюла (она стохастична).
2. Модель добавляла префикс контракта в имя функции (`SimpleBridge.deposit`) и пыталась вызывать `receive()` напрямую (это спец-функция Solidity, срабатывает только автоматически). Оба случая обработаны в `execute_scenario`.
3. **Самый интересный баг — в собственном коде защиты от сбоев.** В `try_parse_scenario()` было `except json.JSONDecodeError as first_error: pass`, а чуть ниже — `raise first_error`. Упало с `cannot access local variable 'first_error'`. Оказалось: Python автоматически удаляет переменную, объявленную в `except ... as имя:`, сразу по выходу из блока `except` (чтобы не было циклических ссылок на traceback) — это малоизвестная особенность языка. Пять прогонов из тридцати в первой полной серии пропали именно из-за этого. Исправлено: сохранять исключение в обычную переменную, объявленную ДО `try`.
4. **Самая содержательная находка фазы — race condition, а не баг контракта.** В нескольких прогонах фаззер докладывал о нарушении INV-2 (`totalLocked != totalMinted`) сразу после ОДНОГО успешного `deposit()`, хотя в самом контракте `totalLocked` и `totalMinted` увеличиваются двумя соседними строками внутри одной атомарной транзакции — расхождение физически невозможно. Проверили гипотезу вручную новым скриптом `test_inv2_manual.py` (деплой → один `deposit()` → сразу читаем состояние, без атаки). Первая версия скрипта тоже не дожидалась `wait_for_transaction_receipt()` после `deposit()` и ошибочно "подтвердила" нарушение — сама попалась в ту же ловушку, которую диагностировала. После добавления ожидания receipt — инвариант оказался соблюдён. Причина найдена: `execute_scenario()` внутри `fuzzer_bridge.py` вызывала `check_invariants()` сразу после `transact()`, не дожидаясь, пока транзакция реально попадёт в блок — из-за этого проверка иногда попадала на "рваный" промежуточный снимок состояния между несколькими последовательными RPC-вызовами. Добавили `wait_for_transaction_receipt()` после всех четырёх видов транзакций внутри `execute_scenario`.
5. После починки #4 — ещё один новый паттерн JSON-сбоя: модель забыла закрывающую `]` у массива `transactions` (`"...}}"` вместо `"...}]}"`). Наивное добавление `]` в конец строки давало неверный порядок скобок (`"...}}]"`) — пришлось вставлять её ПЕРЕД последней `}`, а не после всего. Ещё через один прогон — модель начала вставлять JS-style комментарии (`// ...`) внутрь JSON, что тоже пришлось вырезать регексом до парсинга.
6. **Главное архитектурное решение фазы:** вместо того чтобы продолжать чинить каждый новый способ, которым модель ломает JSON, по одному — добавили `"format": "json"` в запрос к Ollama API. Это режим constrained decoding — модель на уровне генерации токенов не может выдать невалидный JSON. После этого две контрольные серии подряд прошли с 0 инфраструктурных ошибок (до этого — 2-3 из 5 почти в каждой серии). Важно: это ограничивает только СИНТАКСИС ответа, не ограничивает содержание — какие функции вызывать, в каком порядке, с какими суммами, модель выбирает так же свободно, как раньше.
7. Финальная серия на N=30 (уже с `"format": "json"`) дала 2 инфраструктурные ошибки: одна — таймаут `wait_for_transaction_receipt` (120 сек) после 134 минут одной сессии Anvil, вторая — `'NoneType' object is not iterable` (модель прислала `"args": null` — валидный JSON, но `tx.get("args", [])` не подставляет default, если ключ присутствует со значением `null`; исправлено на `tx.get("args") or []`).

**Итог серии на 30 прогонов:** 66.7% находок без подсказки, ещё 23.3% — только с подсказкой, 90% суммарно, 1 полный провал (не системная причина — модель 16 раз подряд просчиталась с масштабом сумм), 2 инфраструктурные ошибки. Число N=30 обосновано формулой доверительного интервала Уилсона (не нормальной аппроксимацией — она ненадёжна на малых выборках).

### Что усвоено

- **Единичный прогон не может выявить статистические/инфраструктурные проблемы** — они проявляются только на сериях. Часть находок этой фазы (гонка состояний, редкие варианты поломки JSON) физически не могла обнаружиться на прогоне 1/1, только на прогонах по 3-5-30.
- **Разделение "формат ответа" vs "содержание ответа" — ключевая идея всей фазы.** Ограничение синтаксиса (constrained JSON decoding) не сужает пространство поиска атак ни на бит — сужает только пространство способов сломать парсер. Это позволило устранить целый класс проблем одним архитектурным решением, а не бесконечной серией точечных патчей.
- **Малоизвестные особенности языка кусают именно в защитном коде.** Баг с `except ... as e` — классический пример того, что код, написанный "для подстраховки от сбоев", тоже нужно тестировать на пути сбоя, а не только на happy path.
- **Подозрительный результат — повод для ручной проверки, а не для того, чтобы сразу писать его в отчёт.** `test_inv2_manual.py` — та же практика, что и `test_bridge_manual.py` в Фазе 6: прежде чем доверять находке автоматики, воспроизвести вручную. В этот раз ручная проверка сама изначально содержала баг (тот же race condition) — хороший урок, что "проверить руками" не защищает от ошибки, если ручная проверка написана так же небрежно с точки зрения ожидания результата транзакции.

### Трудности

Основная трудность этой фазы — количество независимых, не связанных друг с другом причин сбоя (7+ различных паттернов поломки JSON/race condition/Python-особенностей), каждая из которых требовала отдельного прогона для диагностики и отдельного минимального воспроизводящего примера перед фиксом. Растянуто на несколько итераций переписки — но каждая итерация давала однозначный, проверяемый результат перед переходом к следующей.

### Идеи по улучшению

- **Собрать статистику по частоте каждого типа сбоя** — сейчас это качественный список, количественная частота дала бы представление о самых частых паттернах LLM-сбоя.
- **Проверить, не устранит ли `"format": "json"` необходимость части регекс-починок (`sanitize_llm_json`) полностью** — сейчас они оставлены как страховка "на всякий случай".
- Всё ещё актуально: снапшоты Anvil вместо передеплоя на каждой итерации — особенно важно теперь, когда серии выросли до 30 прогонов и заняли больше 2 часов.

## Фаза 6.5 (часть 2) — Echidna, harness, сравнение — 17.08.2026

### Что было сделано

Установили Echidna через `brew install echidna`. Разобрали формат `echidna_*()`-свойств (без аргументов, `bool`, `true`=всё в порядке) и ключевое отличие от нашего Python-подхода: инварианты должны жить прямо в Solidity, а не проверяться снаружи через `w3`.

**Написали `SimpleBridgeEchidnaTest.sol`** — harness-контракт, наследующий/оборачивающий `SimpleBridge`:
- Сам деплоит `SimpleBridge` в конструкторе и регистрирует себя валидатором — иначе Echidna не смогла бы угадать адрес атакующего контракта среди `2^160` возможных значений (она видит только адреса, уже встретившиеся в состоянии).
- Добавили свой счётчик `mapping(bytes32 => uint256) withdrawHits` — у оригинального `SimpleBridge` есть только флаг `processedMessages` (bool), а Echidna не умеет анализировать историю событий, только текущее состояние.

**Критическая находка на ревью, до первого прогона:** в первой версии harness'а `receive()` реентрировал безусловно при получении любого ETH — Echidna не нужно было НИЧЕГО "решать" про атаку, только найти порядок из двух вызовов (`doDeposit → doWithdraw`). Это делало бы сравнение нечестным: LLM должна была сама решить вызвать `setAttackParams` с ненулевым `maxReentries`, а Echidna получила бы эту атаку "бесплатно", встроенной в контракт. Исправили: добавили `armReentry(uint8)` — реентранси стала opt-in, прямой аналог `setAttackParams()`.

**И снова та же ловушка, что уже была с `fuzzer_bridge.py`:** после отправки исправленной версии harness'а первый прогон всё равно нашёл баг за 2 вызова (`doDeposit → doWithdraw`, без `armReentry`). Проверили: `grep -c "armReentry" contracts/SimpleBridgeEchidnaTest.sol` → 0. Файл не был заменён — скачали не тот. Повторили ещё раз (снова не тот файл, 0), прислали файл ещё раз явно отдельным сообщением, проверили `grep` перед прогоном — только тогда получили честный результат.

**Настроили `echidna.yaml`:** нашли и исправили неверный комментарий (`maxGasprice` ошибочно объяснялся как "разрешение отправки ETH" — на самом деле это цена газа случайных транзакций, ETH-переводы в payable-функции разрешены у Echidna по умолчанию, отдельно включать не нужно). Добавили `corpusDir` — сохраняет найденные последовательности вызовов между запусками.

**Серия N=10 независимых прогонов** (`--test-limit 50000`, отдельный `--seed` и `--corpus-dir` на каждый, чтобы не переиспользовать чужой корпус): 10/10 (100%) нашли INV-3. Время до находки (по временным меткам компиляции/`falsified!` в логе, не полное время прогона — Echidna в property-режиме продолжает работать до `testLimit` даже после первой находки, чтобы проверить остальные свойства) — стабильно ~1.14–1.25 сек, среднее ~1.18 сек.

**Разбор находки — почему так быстро, и что это на самом деле означает** (самая содержательная часть этой сессии): три отдельных, не сводимых друг к другу вывода:
1. Скорость сама по себе ничего не говорит о превосходстве case перебора — пространство поиска после ручной подготовки harness'а крошечное (4 функции, 3 логических шага), и на такой глубине случайный и направленный поиск неразличимы.
2. Настоящая разница — в том, кто проделал интеллектуальную работу по подготовке минимального пространства поиска: harness под Echidna писал человек (несколько итераций правок), LLM получила эквивалентную подготовку автоматически через Slither.
3. Ещё одна асимметрия, которую нельзя устранить без смены парадигмы: `currentMessageId` в harness — общее состояние контракта, Echidna не нужно "согласовывать" его между вызовами, как приходилось LLM (совпадение строкового алиаса `"m1"` в разных JSON-транзакциях, источник многих прошлых ошибок в Фазе 6.5 часть 1).

**Параллельно перепрогнали LLM-фаззер ещё на N=10** (та же, не изменившаяся методология) — 40.0% без подсказки (против 66.7% в серии N=30). Доверительные интервалы двух серий широко перекрываются — не статистически значимая разница, а ожидаемый разброс на малых выборках. Объединили в N=40: 60.0% без подсказки [44.6%, 73.7%], 92.5% всего [80.1%, 97.4%] — заметно точнее любой из двух серий по отдельности.

### Что усвоено

- **"Проверьте, что реально выполняется актуальный файл" — универсальное правило, не специфичное для Python.** Та же ошибка (скачал не тот файл из истории переписки) повторилась на Echidna/Solidity ровно так же, как несколько раз повторялась на `fuzzer_bridge.py` в части 1. `grep -c` перед интерпретацией результата — дешёвая и обязательная проверка на любом инструменте.
- **Harness для классического фаззера — это не нейтральная инфраструктура, а часть эксперимента.** Решение "делать ли реентранси условной или безусловной" напрямую определяет, что именно измеряется — способность найти атаку или способность найти двухшаговую последовательность вызовов при уже готовой атаке. Это легко упустить, потому что и то и другое выглядит как "Echidna нашла баг".
- **Разные независимые серии одного и того же эксперимента нужно объединять, а не выбирать более удобную.** N=10 показал более низкий % без подсказки, чем N=30 — соблазн был бы говорить только о "лучшем" результате; правильная практика — объединить в N=40 и работать с более узким, но честным интервалом.
- **Доверительные интервалы — это инструмент, который защищает от неверных выводов, а не формальность для отчёта.** Именно широкое перекрытие ДИ между N=30 и N=10 не позволило сделать неверный вывод "модель стала хуже искать сама".

### Трудности

Дважды подряд впустую потраченное время на интерпретацию результата не того файла — при том, что ровно такая же проблема уже случалась (и была задокументирована) в части 1. Стоит на будущее заводить такую проверку сразу первым шагом после любой правки кода, а не как реакцию на подозрительный результат постфактум.

### Идеи по улучшению

- Явно замерить время ДО первой находки, а не только полное время прогона, во всех последующих сравнениях Echidna (в этой серии пришлось выковыривать это вручную из временных меток лога — стоит добавить `--stop-on-fail` или парсить это автоматически в отдельном скрипте по аналогии с `run_bridge_stats.py`, если понадобится ещё серия).
- Если останется время — попробовать harness с бОльшим пространством поиска (больше "шумовых" функций, более длинные `seqLen`), чтобы проверить, начинает ли разница между Echidna и LLM проявляться на более глубоких сценариях, ближе к исходному тезису работы про 10-шаговые атаки на реальных мостах.

## Дополнение к Фазе 6.5 (часть 2) — выравнивание N до 40 с обеих сторон — 18.08.2026

### Что было сделано

После получения первых 10 прогонов Echidna (100% успех, ~1.18 сек в среднем) встал вопрос честности: у LLM-фаззера была выборка N=40 (30+10), а у Echidna — только N=10. Для корректного сравнения выборки должны быть сопоставимого размера, иначе доверительные интервалы несравнимы по построению (у Echidna N=10 в принципе не может дать такую же узкую погрешность, как N=40, даже при одинаковом истинном проценте успеха).

Посчитали заранее, какую точность даст N=40 для Echidna при разных возможных исходах (формула Уилсона) — если все 40 найдут баг, ДИ будет [91.2%, 100.0%] (±4.4 п.п.), заметно точнее, чем у LLM. Дозапустили ещё 30 прогонов Echidna (seed 11-40, отдельный `--corpus-dir` на каждый, как и раньше) поверх уже имеющихся 10 (seed 1-10).

**Результат: все 30 новых прогонов тоже нашли баг — итог 40/40 (100%), 95% ДИ [91.2%, 100.0%].** Время до находки осталось таким же стабильным, как в первой серии — среднее 1.20 сек, медиана 1.15 сек, разброс всего 1.10–2.15 сек (один выброс на 2.15 сек, не разбирали отдельно — в пределах ожидаемого шума для системы с несколькими воркерами).

Заодно подтвердили точным замером по времени (не только медианой), что финальный N=40 LLM-фаззер даёт: среднее 256.3 сек, медиана 250.3 сек, разброс 29.0–1351.7 сек (более чем 45-кратный разброс между самым быстрым и самым медленным прогоном — сильная иллюстрация стохастичности генерации по сравнению с Echidna).

**Финальная таблица сравнения (N=40 с обеих сторон):**

| Метрика | Echidna (N=40) | LLM-фаззер (N=40) |
|---|---|---|
| Успех | 40/40 (100.0%), ДИ [91.2%, 100.0%] | 37/40 (92.5%), ДИ [80.1%, 97.4%] |
| Среднее время | 1.20 сек | 256.3 сек |
| Разброс времени | 1.10–2.15 сек | 29.0–1351.7 сек |

### Что усвоено

- **Сравнивать выборки разного размера напрямую — методологическая ошибка, даже если проценты выглядят убедительно.** N=10 против N=40 недопустимо сравнивать как равнозначные цифры в таблице, даже если оба процента "хорошие" — доверительные интервалы будут разной ширины по самой конструкции формулы, независимо от истинных значений.
- **Разброс (min-max, не только среднее/медиана) — самостоятельная содержательная метрика, а не просто побочная цифра.** 45-кратный разброс времени у LLM против почти нулевого у Echidna — это отдельный, важный пункт сравнения "по принципу" (стохастичность vs детерминированность), который легко упустить, если смотреть только на среднее.
- Заранее посчитанная точность при N=40 (до того, как гонять прогоны) оказалась полезной не только как обоснование выбора N, но и как ожидание, с которым можно было сверить реальный результат — совпадение расчёта [91.2%, 100.0%] с фактическим итогом подтверждает, что формула применена верно.

### Следующий шаг (Фаза 7)

Данные полностью финализированы, сравнение выровнено по N с обеих сторон. Дальнейшая работа — только сборка итогового отчёта, новых экспериментов больше не требуется.
