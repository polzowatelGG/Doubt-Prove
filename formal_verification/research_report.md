# LLM-генерация формальных спецификаций для верификации смарт-контрактов

## Аннотация

Работа посвящена разработке пайплайна, который извлекает структуру Solidity-контракта, формирует кандидаты формальных свойств с помощью локальной языковой модели, переводит их в Certora Verification Language и итеративно уточняет по результатам формального верификатора. Исследуется не только синтаксическая компилируемость спецификаций, но и их семантическая полезность: способность обнаруживать нарушения экономических инвариантов и последовательностных свойств, включая повторный вывод средств с одним nonce. Эксперимент строится на упрощённой модели L1↔L2-моста и наборе мутированных контрактов.

## 1. Введение

Формальная верификация позволяет проверять свойства программы для символических входов и состояний, а не только для конечного набора тестовых примеров. Однако практическое применение ограничивается стоимостью создания спецификаций. Автор CVL должен понимать Solidity, модель EVM, бизнес-логику протокола и ограничения SMT-решения. Языковые модели потенциально способны снизить этот порог, но их ответы подвержены синтаксическим ошибкам, выдуманным интерфейсам и неверным инвариантам.

Отсюда возникает задача построить контролируемую систему, в которой LLM не считается доверенным компонентом. Она генерирует кандидаты, а компилятор и Prover выступают машинно проверяемой обратной связью.

## 2. Объект, предмет и цель

**Объект исследования:** процесс формальной верификации Solidity-смарт-контрактов.

**Предмет исследования:** методы автоматической генерации и итеративного уточнения CVL-спецификаций с использованием локальной LLM.

**Цель:** разработать и экспериментально оценить пайплайн Solidity → структурированное представление → LLM → CVL → Certora → feedback.

## 3. Задачи

1. Реализовать извлечение AST, ABI и storage layout через стандартный JSON-интерфейс solc.
2. Выделить публичные функции, состояния, события, модификаторы и типы.
3. Разработать constrained prompt и JSON-схему ответа.
4. Сохранить полный `.spec` и перечень свойств.
5. Интегрировать вызов Certora CLI.
6. Классифицировать proof result и диагностику.
7. Выполнить не менее трёх итераций уточнения.
8. Проверить свойства модели моста.
9. Сравнить базовые и итеративные режимы.
10. Оценить спецификации через mutation testing и экспертную разметку.

## 4. Научная новизна

Новизна состоит не в применении LLM к коду как таковом, а в комбинации:

- compiler-grounded представления вместо только сырого текста;
- строго типизированного ответа;
- разделения генерации естественно-языкового свойства и CVL;
- обратной связи от формального инструмента;
- запрета автоматически ослаблять нарушенное свойство;
- оценки через способность различать корректный контракт и мутант.

## 5. Гипотеза

Трёхитерационный режим с AST+ABI повысит Compile@3 и mutation score по сравнению с однократной генерацией, но не устранит необходимость экспертной проверки бизнес-инвариантов.

## 6. Модель угроз

Рассматриваются:

- повторное выполнение withdrawal;
- нарушение покрытия обязательств залогом;
- неверное обновление агрегированных балансов;
- обход авторизации;
- reentrancy на внешнем переводе;
- нулевые операции;
- ошибочные или вакуозные спецификации LLM.

Не рассматриваются полностью:

- консенсус L1/L2;
- корректность relayer и fraud/validity proof;
- реорганизации;
- криптографическая безопасность;
- вся межцепочечная система без отдельной модели сообщений.

## 7. Архитектура

Пайплайн состоит из анализатора Solidity, генератора prompt, Ollama-клиента, валидатора JSON, Certora runner, парсера результатов и оркестратора. Каждая итерация сохраняет prompt, ответ модели, `.spec`, вывод Prover и итоговый статус. Такой журнал обеспечивает воспроизводимость.

## 8. Формализация свойств

### 8.1 Покрытие

Для абстрактной модели:

`totalMintedL2 <= totalLockedL1`.

Это свойство допустимо только при явно заданной семантике переменной `totalMintedL2`. В реальном мосте состояние находится в другой цепочке, поэтому необходим ghost-state либо композиционная модель двух контрактов.

### 8.2 Уникальность nonce

Для любого nonce не существует последовательности, в которой два вызова `finalizeWithdrawal` с этим nonce завершаются успешно.

Это не обычный state invariant, а последовательностное правило с двумя вызовами.

### 8.3 Сохранение баланса

При успешном deposit приращение `totalLockedL1` должно совпадать с `msg.value`. При успешном withdrawal уменьшение должно совпадать с amount, если моделируемый внешний перевод завершился успешно.

## 9. Feedback loop

На первой итерации модель генерирует минимальную спецификацию. При compile error в prompt возвращается точная диагностика и ABI. При counterexample модель должна классифицировать причину:

1. реальный дефект контракта;
2. слишком сильное свойство;
3. недостаточная модель окружения;
4. ошибочная предпосылка;
5. ложный контрпример из-за havoc/summary.

Система запрещает без объяснения ослаблять assert или добавлять require, исключающий контрпример.

## 10. Эксперимент

Сравниваются режимы Raw-1, AST-1 и AST-Feedback-3. Для каждого контракта выполняется несколько повторов. Метрики: Compile@k, semantic validity, mutation score, число ручных правок, время, токены, timeout rate и vacuity rate.

## 11. Ожидаемые результаты

Ожидается, что AST+ABI резко снизит число выдуманных имён и типов, а feedback loop исправит значительную часть синтаксических ошибок. Наиболее сложными останутся экономические свойства, моделирование внешних вызовов и различение реального дефекта от неполной модели.

## 12. Практическая значимость и Bug Bounty

Пайплайн может использоваться как генератор кандидатов для аудитора: он ускоряет построение первых спецификаций и поиск контрпримеров. Для Bug Bounty результат должен проходить ручную валидацию, воспроизводиться на фиксированном commit и включать минимальный exploit trace. Автоматически найденный counterexample ещё не является подтверждённой уязвимостью.

## 13. Заключение

LLM целесообразно использовать не как доказатель, а как генератор формальных гипотез. Доверенная часть системы остаётся за компилятором, спецификационным type checker и формальным Prover. Научная ценность работы определяется измеримым сравнением режимов и анализом ошибок, а не единичной демонстрацией успешной генерации.
