# LLM + формальная верификация смарт-контрактов

Исследовательский прототип автоматической генерации CVL-спецификаций из Solidity-кода и итеративного уточнения спецификаций по результатам Certora Prover.

## Исследовательский вопрос

Может ли локальная LLM автоматически извлекать из Solidity-кода содержательные экономические и безопасностные свойства, переводить их в CVL и улучшать спецификацию после получения диагностик или контрпримеров?

## Гипотеза

LLM с AST-представлением контракта, ограниченным JSON-форматом ответа и циклом обратной связи создаёт больше компилируемых и содержательных спецификаций, чем однократная генерация по сырому исходному коду.

## Архитектура

1. `solc --standard-json` строит AST, ABI и storage layout.
2. `SolidityAnalyzer` извлекает функции, переменные состояния, события и модификаторы.
3. `PromptBuilder` формирует структурированный запрос.
4. Ollama генерирует кандидата `.spec` и список инвариантов.
5. `CertoraRunner` запускает `certoraRun`.
6. `ResultParser` классифицирует результат: `VERIFIED`, `VIOLATED`, `COMPILE_ERROR`, `TIMEOUT`, `UNKNOWN`.
7. Диагностика/контрпример возвращается в LLM; выполняется минимум три итерации.
8. Все артефакты сохраняются в `results/<run_id>/`.

## Быстрый запуск

Требования:

- Python 3.11+
- `solc` версии, совместимой с контрактом
- Ollama и локальная модель
- для реального Certora: `certora-cli` и переменная `CERTORAKEY`

```bash
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

ollama pull llama3.1:8b
python -m src.llm_cvl.cli analyze contracts/SimpleBridge.sol
python -m src.llm_cvl.cli run contracts/SimpleBridge.sol \
  --contract SimpleBridge \
  --model llama3.1:8b \
  --iterations 3 \
  --mode mock
```

Реальный запуск:

```bash
export CERTORAKEY=...
python -m src.llm_cvl.cli run contracts/SimpleBridge.sol \
  --contract SimpleBridge \
  --model llama3.1:8b \
  --iterations 3 \
  --mode certora
```

## Что проверяется на тестовом мосте

- `totalMintedL2 <= totalLockedL1`;
- успешный депозит увеличивает обе агрегированные величины на одинаковую сумму;
- один и тот же `nonce` нельзя успешно вывести дважды;
- успешный вывод уменьшает залог ровно на сумму вывода;
- нулевая сумма депозита/вывода должна отклоняться.

Контракт намеренно содержит вариант уязвимости: отметка `processedWithdrawals[nonce]` выполняется после внешнего вызова. Это создаёт модельную основу для исследования повторного выполнения/reentrancy. Для строгого межцепочечного свойства требуется модель L2 или ghost-state; один L1-контракт сам по себе не доказывает корректность всей системы.

## Метрики эксперимента

Основные:

- Compile@1 и Compile@3: доля CVL-файлов, прошедших синтаксическую/типовую проверку;
- Valid-property rate: доля свойств, признанных экспертом содержательными;
- Proof outcome: verified / violated / timeout / vacuous;
- число итераций до компилируемой спецификации;
- количество ручных правок;
- mutation score: доля искусственных дефектов, обнаруженных спецификацией;
- ложноположительные свойства и некорректные предположения.

Сравниваются три режима:

- A: сырой Solidity → однократная генерация;
- B: AST + ABI → однократная генерация;
- C: AST + ABI + обратная связь, 3 итерации.

## Ограничения

- Certora Prover является облачным сервисом; реальный прогон требует ключа и сети.
- Код не гарантирует, что произвольный LLM-ответ будет корректным CVL; он валидирует формат, сохраняет версии и передаёт ошибки обратно модели.
- Контрпример не всегда означает ошибку контракта: причиной может быть слишком сильная или неверно сформулированная спецификация.
- Доказанное свойство может быть вакуозным, если предпосылки недостижимы.
- Для внешних контрактов, мостовых сообщений и межцепочечного состояния нужны summaries, ghosts или отдельная модель окружения.
